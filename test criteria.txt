ONEPLACE BACKEND API TEST CRITERIA
==================================

Scope: direct requests to each service, then the same public routes through the API gateway. Run against isolated H2 databases and isolated upload/snapshot directories. Use a unique email and unique titles for each run. Do not run write tests against production data.

Common expected results for every route in the inventory below:
- GET: HTTP 200 with the documented JSON or file response, unless the named item is missing (404). A read does not change database state. Repeat after service restart to verify persisted records are returned.
- POST: HTTP 200 (or the route's declared success status) and a response body with the created/updated ID or result, except void actions. Read the item back, restart the service, and read again to prove persistence. Invalid input must produce a 4xx response and no new record or file.
- PUT: HTTP 200 with updated values. Read back and restart to verify persistence. Wrong owner or invalid input must not change the original record.
- DELETE: 2xx with no unhandled exception. A subsequent read must show the item absent or the relationship removed. Restart to confirm deletion persists.
- Authenticated routes: no token returns 401; a wrong role returns 403 where role restricted. Other users must not see private notes, drafts, carts, or orders.
- Multipart and media routes: upload bytes, read/download bytes, compare size/content, and verify files survive restart. Bad media type or missing file returns 4xx without a persisted file reference.
- Exception check: no 500 response, stack trace, or inconsistent partial DB state for a valid request; negative cases return the expected 4xx response.

Cross-service criteria:
1. Gateway -> each service: call the route with the same token and body through port 8080 (or the isolated gateway port). Expect the same status and response as the direct service call.
2. Classroom -> auth: register teacher/student, create topic and comment; author names should match the account/JWT name, and the public display-name lookup used for legacy topics should return the teacher's name.
3. Classroom -> feed: create a classroom lesson, list feed; legacy lesson appears once, with stable ID after repeated requests.
4. Studio -> feed: teacher creates a draft and publishes it; feed returns one post with sourceDraftId, and republishing is idempotent.
5. Quiz -> feed: teacher creates quiz, publishes a feed post with quizId; student starts and submits the quiz and reads persisted result.
6. Cart -> catalog -> delivery: seller creates stocked product; buyer adds to cart, prepares and completes payment. Stock decreases once, order persists, delivery order is readable, and repeated completion does not duplicate reservation or delivery.
7. Failure path: invalid service key on catalog inventory/delivery returns 403 with no DB change. If delivery is unavailable during checkout, the paid order remains durable, checkout returns promptly, and cart retries the idempotent delivery notification when delivery returns. If catalog is unavailable before payment, checkout fails without confirming an order.

OBSERVED RESULTS (2026-10-23)
-----------------------------
Environment: isolated services on ports 18080-18088, separate temporary H2 databases and upload directories. Discovery was also started on 18761. Existing application data was not used for write tests.
Build: all nine API service boot jars compiled successfully. Discovery health returned 200 and /eureka/apps returned 200.
Automated API run: Backend/api-smoke-test.py -> 121/121 checks passed. Every controller route above was exercised directly or as part of a service-to-service request. Gateway proxy calls to auth, catalog, cart, classroom, feed, studio, quiz, and delivery returned expected responses. Classroom lessons appeared in feed exactly once across repeated reads.
Responses and state: success responses were 200; expected rejection responses were 401, 403, 404, or 409 as asserted. Created records were read back; deleted records disappeared; buyer checkout reduced catalog stock, cleared the cart, created a durable order, and created a delivery record. Cancellation restored reserved stock. Uploaded photo, product image, classroom material, topic resource, classroom video, and feed media bytes were downloaded and compared with uploads.
Persistence after restart: catalog service was restarted against the same isolated H2 database. Product ID 36 retained its updated name, stock=4, and image file reference. A prior restart also returned matching values through the gateway for product ID 6.
Failure and recovery: delivery service was stopped during checkout. Cart returned HTTP 200 for durable paid order ID 34 in 0.03 seconds, then retried publication after delivery restarted; delivery GET returned order ID 34. Catalog was stopped before payment preparation: cart returned HTTP 503 and the buyer's order count remained unchanged. Invalid internal service keys returned 403 without a valid write.
Inventory completeness: the 86 method/path entries above exactly matched the 86 operations returned by the eight API services' /v3/api-docs endpoints (12 auth, 9 catalog, 9 cart, 31 classroom, 12 feed, 4 studio, 6 quiz, 3 delivery). The gateway's /api/** proxy was checked separately through all eight services.
Defects found and corrected: exception responses were incorrectly converted to 401 by JWT filters; quiz creation returned recursively serialized malformed JSON; delivery had an unintended default security gate; public display-name lookup was blocked; Kafka absence delayed delivery requests; and cart lacked a durable delivery publication retry.
Infrastructure limit: no Kafka broker was available, so Kafka event consumption itself was not verified. Eureka registry health and API were checked; API services in this isolated run used explicit URLs with Eureka registration disabled, so dynamic service registration/load balancing was not verified.
Reproduction: from the repository root run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File Backend/run-api-tests.ps1`. The launcher builds jars, starts isolated services, waits for health, runs `python -u Backend/api-smoke-test.py`, and stops only its own Java processes. Use `-SkipBuild` to reuse current jars. The script generates unique account emails each run and exits nonzero on a failed assertion. The clean launcher run completed 121/121 checks and stopped 20 isolated Java processes.
